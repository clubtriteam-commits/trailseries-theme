# Independent audit — trailseries.bg rebuild

- Date: 2026-11-12
- Scope: `wp-content/plugins/trailseries-results`, `wp-content/themes/exhibz-child`, `migration/`, docs, git history (165 commits, 2026-07-02 → 2026-08-28)
- Mode: read-only. Nothing was modified, committed or deployed; staging and production were not contacted. This file is the only thing written to the repo.

## Verdict

**Not ready to launch.** The code is tidier than most AI-built WordPress projects (validated schema, escaped output, nonces and capability checks on every admin action, no secrets or personal data in git), but four things block a cutover. (1) The legacy-URL guarantee of ADR-003 rests on `'rewrite' => ['slug' => '']`, which WordPress core replaces with the post-type name, so result pages are most likely served at `/ts_result/{slug}/` and old URLs only "work" through a redirect that the crawl-diff script accepts as a pass. (2) The category corrections from the August audit never reach WordPress: the importer builds post titles from the raw heading, not the corrected one, so 49 result pages would show two or more sections with the same label and 12 posts get a wrong distance. (3) Season rankings are computed per calendar year while seasons 1–8 span two years, and bonus races exist only for 2025, yet 33 legacy standings URLs redirect to that recomputed page. (4) There is no test suite, no cutover runbook, no rollback plan, and the one verification script that exists currently fails. Items 1 and 2 are each a one-to-two-day fix; item 3 needs a decision from you first.

## Update 2026-11-12 — H11 verified and fixed on staging

**What was exposed.** Before the fix, `https://stg.trailseries.bg/migration/data/canonical/_manifest.csv` and `/.git/HEAD` both returned `200`. The manifest on the server was dated 2026-07-03, so the results data (names and ages) had been downloadable for about four months. `/.htaccess.bak-20260823` was also served.

**What was in the docroot `.git`.** A fetch of this repository from GitHub (134 commits up to `45d75a5`), an unborn `master`, and 157 files staged but never committed. `wp-config.php` was neither staged nor in history; no sensitive paths; zero matches for credential patterns. Nothing beyond what is on GitHub could be taken from it.

**What was in `migration/data/`.** Four copies of the results data: `canonical/` (909 JSON, July), `canonical_fixed/` (904 JSON, 22–23 August), 896 loose JSON files directly in `data/` (July) and two zips (653 and 901 files), plus a PHP `error_log`. No WXR export and no credentials file.

**What was done on staging.**

1. Added a "TSR security" block at the top of the docroot `.htaccess`: `RedirectMatch 404 ^/migration(/|$)` and `RedirectMatch 404 (^|/)\.git(/|$)`. Previous file saved as `/home/trailser/htaccess-stg.bak-20261112`.
2. Moved the whole `migration/` directory (2,730 files, 20 MB, count identical before and after) to `/home/trailser/tsr-data/migration/`, mode 700, outside the docroot. Nothing was deleted from it.
3. Moved `.htaccess.bak-20260823` to `/home/trailser/`.
4. Deleted the docroot `.git` (8.4 MB) after confirming it matched the inspection above.

Result: `/migration/…`, `/.git/HEAD` and `/.htaccess.bak-20260823` return `404`; `/`, `/rezultati/`, `/klasiraniya/` and `/traseta/` return `200`.

**What was changed in the code (local, not committed, not deployed).** `class-cli.php` `bulk_import()` no longer defaults to `ABSPATH/migration/data/canonical/`. It reads `TSR_DATA_DIR` from `wp-config.php` or requires both `--manifest` and `--json-dir`, and refuses any path inside the web root. `TSR_DATA_DIR` is not yet defined on staging.

**Still open.**

- Whether anyone downloaded the data between July and October **cannot be determined**. Logs checked on 2026-11-13 (see below). The data could have been taken in that window without leaving any record now.
- Three of the four data copies on the server are redundant; which to delete is the owner's call.
- Whether the GitHub repository is public or private was not checked.
- Production must be set up with the same rule from day one (add to the cutover runbook, B5).
- `TSR_DATA_DIR` is not yet defined in the staging `wp-config.php` (the code change itself is deployed: the live `class-cli.php` matches `b257ccf`).

**Access logs (checked 2026-11-13).** cPanel keeps one raw log per vhost in `~/access-logs/` (→ `/usr/local/apache/domlogs/trailser`). It is rotated monthly and not archived (`~/logs/` holds only the PHP error log). The staging HTTPS log `stg.trailseries.bg-ssl_log` therefore starts on 2026-11-01, so nothing from July–October survives. AWStats (`~/tmp/awstats/awstats{07..11}2026.stg.trailseries.bg.txt`) is no substitute: it parses only the plain-HTTP log, and it does not list even the November `.git` hits that are in the raw log.

For 1–13 November:

- `/migration/…`: no `GET` returned `200` to anyone. The only `200`s are `HEAD` requests from the fix session itself (62.73.69.213, 12 Nov 22:24). The one later request, `GET /migration/data/canonical/_manifest.csv` from 98.91.77.46 at 23:42 (UA `Mozilla/5.0 (compatible)`), got `404`. It was probably a verification fetch, but that is not confirmed.
- `/.git/`: automated scanners fetched `/.git/HEAD` with a `200` six times from six IPs (2–11 Nov), and probed `/.git/config` from about ten more. Every `/.git/config` and `/.git/objects/info/packs` request was answered `406` (the host's ModSecurity), so no objects or config were served. The `.git` had nothing that isn't already on GitHub in any case (see above).
- `/.htaccess.bak-20260823`: requested only by the fix session.

Scanners do look for `.git` routinely; `/migration/data/canonical/_manifest.csv` is not a path scanners guess. Reaching it would have needed the path to be known, or directory listing to be enabled on `/migration/`, which was not tested before the files were moved.

## What I checked that turned out fine

- **Tier 0 slug-lookup bug**: fixed in `342640f` (2026-07-10). `class-cli.php:281-282` looks up `sanitize_title( $post_slug )`. The memory note calling it a blocker is stale. I emulated the stored-slug derivation for all 904 files: no two sections collide, and no page slug is a dash-prefix of another, so hub matching by prefix is sound.
- **Schema and validation**: `TSR_Result_Row` / `TSR_Result_Set` reject unknown keys, bad statuses, bad times and ragged splits; `TSR_Repository::save()` round-trips. The renderer escapes every cell.
- **Admin actions**: both steps of the uploader, the track-labels page and the partner URL box check capability and nonce. Uploaded files are parsed from the temp path, never moved; extension and 10 MB size are checked.
- **SQL**: the only query with a variable uses `$wpdb->prepare()` with `esc_like()` (`single-ts_result.php:54-61`). No AJAX or REST endpoints are registered; `_tsr_result_set` is not exposed through REST.
- **Git history**: every path ever committed was listed; no results data, WXR, SQL dump or credentials. `migration/data/` is ignored.
- **Syntax**: `php -l` clean on all 45 PHP files (PHP 8.3), `py_compile` clean on all 9 Python scripts, `node --check` clean on the one JS file. No debug output left in the code.
- **URL inventory**: all published pages and posts in the WXR are in the inventory except one (`/2098/`).
